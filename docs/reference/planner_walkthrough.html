Planner Walkthrough

One diagram, and a few sentences on each box in it. The planner turns reception.json into strategy.json: one language-model call that decides how many columns, in what bands, pinned to which stations, and whether the study can answer the question — never a coordinate. It touches exactly one server: the model reception chose.

The boxes, top to bottom

reception.json → _summary_for_prompt

The planner is shown the brief and observations_summary — counts, station ids, coordinates, elevations, in-basin tags — and nothing else from the package. Not the grid, not the rain, not the observation series (170 KB for one basin), not the subsurface. It stratifies on elevation and pins by station id, so those are all it needs; everything else would be paid for and unread. The exclusion is done twice on purpose: by naming keys, and by popping the data siblings if they were ever written into the brief by mistake.

model server · brief.model → describe_server

The one server the planner touches, asked once. _model_report calls the same local describe_server reception used, by the name reception wrote, and memoizes it — two blocks are read out of one report, and a report costs a real round trip. Nothing goes through a manager class: until 2026-08-17 it did, and since the only manager was ELM's, every study was handed ELM's rules under a heading saying they came from the model that would run. For PFLOTRAN those rules are not stale but inverted.

pinning

What a column of this model may be compared against at a point, and what not, each with a reason and a basis — physics, or a design decision about how columns are spent. It decides which variables may get stations, and the instead word gives the verdict for the rest. If the report has no such block the planner is told so, writes a plan anyway, and the sampler refuses to place a pinned column until it can read one.

constraints

What a plan may not vary: fixed (mechanisms the model does not have — a question that needs one is infeasible), forcing, soil, initial_state, each with chosen_by (the model, the plan, or a split), available, and a consequence sentence to reason from. The prompt tells the model how to read the block and adds no limit of its own — a limit not in the block is not a limit. This is where a stale report moves the plan: on 2026-08-18 PFLOTRAN's block still said depth_cap_m: 50 after the framework had gone to 392 m, and the verdict came back partial for a reason that no longer existed. The server was corrected; the planner needed no change.

the LLM call

Purely a proposal — nothing here corrects it. Its system prompt is planner.txt with the two blocks appended under labelled headings; its user message is the summary. On a site it decides: the band count from relief (3 under 500 m, 4 under 1,200 m, else 5), three columns per band, up to four pinned stations chosen from the summary and filtered by what is pinnable, a verdict per variable, and the feasibility judgement with its requires list. The total is arithmetic — n_bands × per_band + n_validation + 2, the two being the sampler's own water-table anchors — bounded 6..24 as a sampling range, not a compute one, so a cheap model does not get a wider one. On a conceptual request it copies reception's sweep verbatim; the user was shown those levels and said yes.

7 keys → plan["pinning"] → strategy.json

The model's JSON is parsed; the coordinator adds the pinning block it was shown and writes the file. So strategy.json carries the design and the rulebook it was designed against, the same object, and the sampler enforces that copy rather than fetching the rule again. Two readers, one record; a server updated between plan and run, or a resume a week later, cannot make them disagree.

gate · check()

Not the planner — the Experiment Manager's first step, and the only place that holds reception and strategy together. Pure code. It stops a design that would produce garbage (no domain, no period, a count that cannot be placed, a sweep with one level) and corrects what is unusable but survivable — a column count the user stated that the planner ignored, a station named that was never fetched — and records every correction in the run, because the planner is pure LLM and this is the only point a discrepancy becomes visible.

Only two rows come from a server, and both from the same one. A wrong pinning moves the pins; a wrong constraints moves the verdict. Neither can move the band count or the total — on the same basin those came out identical for both models, 5 × 3, + 2.

Two things not on the diagram

It is proven on both models. The same method, driven on the latest ELM and PFLOTRAN receptions on 2026-08-18: each strategy.json carried its own model's block — ELM pins snow and ET, PFLOTRAN pins the water table alone — and the sampler resolved both from the two files with no server call. After the PFLOTRAN report was corrected the same day, the two stale requires lines vanished and the verdict stayed partial for reasons that are true.

What still names a model. One example value in the output schema ("from_model": "ELM") and a historical note explaining why the limits left the prompt. Neither is a rule. The gate's sweep branch has two ELM-worded messages; sweeps are ELM-only today.
