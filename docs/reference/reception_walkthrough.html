Reception Walkthrough

The boxes, top to bottom

user request

One sentence, as typed. If a study already ran this session, the coordinator also passes a little context — the last run directory, its column count, and any runs still in progress that could be resumed. That is all the model starts with.

LLM loop

A language model with five tools and no data. It may take up to fourteen rounds; when it is done it emits one JSON object. Its job is judgement — what is being asked, which model should answer, where, when — and nothing else. It is told, in its own instructions, that the fetching happens after it finishes and is not its concern.

The steps inside the box are the sections of its prompt. In order:

1 classifyis this a study to design, a question to ask back, a request to analyze an old run, or to resume one? A resume may only name a run that was actually offered to it.
2 archetypesite — a real place; conceptual — a controlled sweep with no place; coupling. This choice later decides whether anything is fetched at all.
2a choose modellist what is installed, read at least two servers' own reports, pick one. It writes the choice, the reason, and — separately — whether that model can be run today. A model that fits and cannot be driven is named anyway; the run stops later with the package saved. Nothing about any model is written in the prompt; the model learns it by reading, every time.
2b settle sweepconceptual only. Ask the chosen server what it can vary, then settle levels, weather and what is held fixed with the person. Never emit a design the user has not seen.
3 domainresolve the watershed. Several matches, an unclear scale, a vague place — ask, do not guess.
4 framethe scientific question in a few lines: goals, processes, candidate drivers.
5 periodthe years to simulate, checked against the chosen model's forcing window from its report. Wholly outside → refuse and ask; partly → clamp and say so; unstated → ask. A column count the user stated is recorded; nothing else is designed. How the model starts is the model's, from its report — not decided here.

tools · local

Three questions the framework answers itself, without contacting a server until one is named. list_servers — what is installed right now, with tool names. describe_server(name) — that server's report, whole and unsummarised, one per call, because a report is 5–10 KB and the loop caps a tool result at 12,000 characters. describe_sweep(name) — what that server can vary in a controlled sweep, as its own JSON. All three are cached for the length of one reception; asking twice returns the same answer marked already_asked.

tools · MCP

Two terrain calls, the only servers the loop may reach: resolve_watershed for a named basin, get_elevation when the request names a bare point or a town. Everything else the framework fetches is fetched by code, below the brief.

human · ask_user

Only when a person is at the terminal. Used for the sweep, for an ambiguous place, and for an unstated period. In batch mode it is absent, and the model records its own defaults in run_settings.conflicts instead.

model servers

Each model's own account of itself. Two tools matter here: describe_*_capabilities — what it simulates, whether it is ready, what a column may be pinned to and why not, what a plan may not vary (forcing years, soil, how it starts) — and describe_conceptual_factors, the sweep menu. Both model servers report the same shape, and reception reads the shape, not either server's contents.

brief

The model's JSON, parsed. Intent, archetype, the chosen model with its reason and its availability, the domain, the period, a stated column count if any, and the framing. Two things are deliberately not the model's to write and are filled by code afterwards: the elevation heterogeneity (from the grid) and the observation summary (from what was fetched).

gate · route == design?

A question back, an analysis of an old run, a resume — these return at once with nothing fetched. Only a design goes on. If the model's reply was not JSON at all, that also routes to a question back, with the first 400 characters kept.

gate · archetype == conceptual?

A controlled sweep has no basin, so nothing is fetched. If the model resolved a watershed anyway — a question that names a region can be read as a sweep — the domain is removed and the removal is written into provenance. That line is what lets a reader tell "nothing was fetched, by design" from "the servers were down": same empty blocks, opposite meanings.

code gather

Four fetches, in this order, plain code, the same for every model. Each writes what it got and a provenance record — tool, arguments, time, outcome — including when it failed.

gather_gridterrain. The basin polygon, then a DEM grid over the bounding box, clipped to the polygon; if too few points land inside, asked again denser. This grid is what the sampler will place columns on; its relief goes into the brief.
gather_precipitationDaymet. Daily rain at every grid point for the period, the calendar stored once. Read by a model that takes the forcing it is handed.
gather_observationsUSGS gauges and daily wells, Fan's long-term wells, SNOTEL, AmeriFlux, and the CONUS2 modelled water table as a GeoTIFF. Every station is tagged in- or out-of-basin against the grid's polygon, once, here. A compact summary — counts, ids, coordinates, never a series — goes into the brief for the planner; the series stay in the package for the analyzer.
gather_subsurfacehydrodata. Five ParFlow CONUS2 fields to 392 m over the basin, cached server-side so a second study of the same basin makes no request. Read by a model that builds columns from it.

Two of these are read by only one of today's models, and are fetched for both anyway. That is a recorded decision — two runs of the same basin should carry the same provenance whatever was decided a moment earlier — and the cost is held by the cache. It is the one thing on this page a reader may reasonably want changed.

outputs

reception.json — the brief and the four gathered blocks with their provenance, written by the coordinator the moment reception returns (and again if the run stops at dispatch, so an honest "cannot drive this model" does not cost the fetching). Beside it, written by the servers: wtd_conus2.tif, the modelled water table, and conus2_subsurface.npz, the subsurface. The planner reads the brief; the sampler reads the grid and the stations; the PFLOTRAN manager reads the rain and the subsurface; the analyzer reads the observations. Nobody fetches again.

Two things not on the diagram

Where reception ends. At the bottom arrow. Whether the chosen model can be run, the plan, the dispatch — those are the coordinator's, in workflow.py, and reception never learns what happened. Today the coordinator refuses any model but ELM at dispatch and saves the package; the run directory is also named before reception chooses, so a PFLOTRAN brief lands in an elm_run_* directory.

What is not yet exercised. No reception has run end to end with the current code for either model — the newest ELM and PFLOTRAN receptions on disk both predate this week's changes. One fresh reception per model is the missing check.
