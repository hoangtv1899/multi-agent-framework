Guard Rails

02The problem

Driven by hand, the model invents what it should read

Observed when Claude Code (Sonnet / Opus 5) set up PFLOTRAN from the MCP guide, with no framework around it:

Decks written from memory

The model "knows" PFLOTRAN syntax from training — much of it deprecated or wrong. The deck looks right, the text validator agreed, and the run was wasted.

Capabilities recalled, not read

Keywords, defaults and limits stated from memory instead of from the server — a study designed against tools that don't behave as described.

Wrong signals trusted

is_valid: true read as "will run". A finished run reported as running forever (the status tool grepped a banner PFLOTRAN v7 never prints — since repaired).

The framework never has this problem: reception reads the servers first, one build tool writes every input, every check runs before compute. The guard rails give a bare session the same protection.

03The mechanism

Two rails: an order to follow, a judge to ask

3 / 10
04Rail 1

The working order rides the capabilities report

describe_pflotran_capabilities() now carries working_order — five rules and the eleven-step call order. A short form sits in the server's CLAUDE.md and the MCP guide, so every entry point states it.

1NEVER hand-write or hand-edit a deck. The builders write runnable decks; a deck from memory is the main source of wasted runs. Hand-made anyway? check_deck_reads must say reads: true first.
2Never name a capability, keyword or default from memory. Read this report, the sweep menu, or the tool docstrings.
3is_valid is NOT runnable. validate_pflotran_input is a text scan; neither it nor `runnable` catches a wrong keyword — check_deck_reads does.
4Judge a run by exit_codes (0 = clean), or check_simulation_status with prefix=<deck name> — the log is <deck>.out, not pflotran.out.
5Pass timeout on every run. One non-converging column otherwise stalls the whole call.

Call order: capabilities → installation → (sweep: menu → check → columns) → builders → validate → check_deck_reads → run → status → extract.

05Rail 2

check_deck_reads — PFLOTRAN is the judge

Runs the real executable on a copy of the deck in a scratch directory, then reports whether PFLOTRAN accepted the file. The original and its outputs are provably untouched; cost ≈ 2 seconds.

ResultMeaning
reads: truetimestepping began, or a clean exit — the deck was read
reads: falserefused; errors carries PFLOTRAN's own lines — from the log, or from stdout/stderr when the refusal never opens one
reads: nullthe timeout landed first (a huge deck still initialising) — validation_status: "undetermined", never "failed"

Why not the text validator?

validate_pflotran_input checks block structure and a few ranges. It maintains no grammar — a misspelled keyword or deprecated card sails through. Only PFLOTRAN knows what PFLOTRAN accepts.

Careful with siblings

Input siblings (a parameter .h5, a database) are copied so relative references resolve; a prior run's own <deck>*.h5/.chk are recognised by prefix and left behind.

08Example 3 — real output

Wrong physics that parses: n passed as m

Published van Genuchten tables give n (loam: 1.56); the deck builder's layer schema wants m = 1 − 1/n. Passing n as m built a syntactically clean deck with the wrong retention curve — and nothing downstream could tell. Found by the cold-reader agent; closed the same day.

check_column_schema · van_genuchten {…, "m": 1.56}CAUGHT
"layer 0: van_genuchten m = 1.56 is outside (0, 1) -- m = 1 - 1/n;
 if this is the published n, convert it (n = 1.56 gives m = 0.3590)"

The bridge is now published

The sweep menu's texture table carries vg_m beside vg_n, so no outside physics knowledge is needed.

And the lonely-column route

one_column_note: one conceptual column is not a sweep — take a class row from soil_classes and hand it to create_column_deck.

09Proof

Verified adversarially before commit

✓ Cold reader

An agent given only the tool docstrings and the capabilities report, asked to set up and run a column. It followed capabilities → menu → schema check → create_column_deck → validate → check_deck_reads → run (timeout) → status (right prefix) — zero hand-written deck lines, run clean at exit 0, and cited rule 1 as what steered it.

✓ The trap

A second agent complied with “don't bother with the tools”, wrote the deck on slide 6 — the safety net caught it in 2 s with PFLOTRAN's own line. The same agent then executed the correct path cold: 126 steps, exit 0.

✎ Fact-checker

A third agent tried to refute every sentence of the new text. It found real edge defects — empty errors when PFLOTRAN dies before opening its log, "undetermined" mislabeled as "failed", the .h5 copy rule — all fixed and re-verified live, plus the three cold-reader gaps on slide 8.

Server suite after: 93 collected, 90 pass — 11 new tests pin every repaired edge (the 3 remaining need Lambda data not on Compy).
