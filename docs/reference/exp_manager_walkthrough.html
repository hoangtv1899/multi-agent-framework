Experiment Manager Walkthrough

One diagram, and a few sentences on each box in it. The Experiment Manager turns strategy.json and reception.json into a run: real coordinates, the model's inputs, the simulations, and one experiment.json the Analyzer reads. It is one sequence of stages in the base class, the same for every model; each model's manager — a small file beside its server — fills three slots and makes one build call. It fetches nothing: everything it needs was written by reception.

The boxes, top to bottom

strategy.json + reception.json → check()

The manager reads two files and the site files beside the second — the WTD raster and the CONUS2 arrays reception fetched. Its config is the brief, the reception package, the strategy, the MCP clients, and the resolved years; nothing else comes in. check() runs first, before any count is read: it holds reception and strategy together and either stops (no domain or period on a site, a count that cannot be placed, a sweep with one level) or corrects and records (a column count the user stated that the planner ignored, a station named that was never fetched). The corrected strategy is what every later line reads — reading the count before the gate once built 17 columns for a request that asked for 2.

materialize · site — the sampler

A pure function of the two files. The grid and the basin polygon come off reception.json as written (fetched and clipped once, by the only component that reaches outside — the manager used to fetch and clip them again, fifty-eight points in and fifty-eight out). Bands and columns per band come from the strategy. A station is pinned only if the planner's verdict for its variable was co-located, the variable is pinnable under the block the strategy carries, and reception tagged the station in_basin; a ghost id raises, because plan and observations disagreeing is not survivable. Two water-table anchors are always appended — the median and the shallow tenth-percentile in-basin Fan depth, placement only. The one outside call is terrain.get_elevation at each pinned station, with the station's reported elevation, then the nearest grid point, as fallbacks.

materialize · conceptual — the server builds

No basin, no grid, no sampling: a controlled sweep is one column per level combination, and what a level becomes — a soil texture of 27 turning into a synthetic surface dataset — is the server's knowledge. So the design crosses to the ELM server twice: check_conceptual_design first, so every reason is named at once before an hour of compute, then build_conceptual_columns. The manager sets warm_start = False here: a sweep starts cold, or it is not controlled. The cost — years to forget ELM's defaults, so a short run reports the initialisation as much as the soil — is recorded as a caveat, not fixed with a spin-up.

_refine_columns — the one build call

Where the two managers differ, and the only place. It runs inside materialize, before columns.json is written, because ELM's warm start moves every column 250–400 m onto its donor gridcell — anything persisted earlier describes a plan the run will not follow.

Same shape both sides: coordinates in, inputs out, run plan back. Until 2026-08-18 the PFLOTRAN manager did the join itself in a 117-line _to_run_plan and handed the server pre-chewed columns; moving it made the two managers the same size and the same shape.

columns.json · sampling_design.png

columns.json is written twice, to 01_inputs/ and the run root, and it is the post-build list: the columns as the build call left them — for ELM snapped, with the donor's soil; for PFLOTRAN at the sampled coordinates, with the water table, the forcing and the deck's warning attached. It is the one seam the package reads: the base carries these onto the rows through an asserted list — COLUMN_METADATA for what the sampler writes, plus each manager's COLUMN_METADATA_EXTRA for what its build call adds — and a key neither names raises rather than vanishing. The design figure is drawn after it, by ELM's own code (sampling_design.render_run, imported from beside the server): the columns over a hillshade, forcing against donor elevation, the initial soil water read out of each finidat, the donor soil profiles — all post-warm-start, which is why it cannot run earlier. Non-fatal: a figure is not worth a finished materialize. PFLOTRAN has no figure yet.

_to_run_plan → assumptions.json · run_plan.json

Both managers hand back the plan the server already built rather than recompute it — the same computation twice would be two chances to disagree. The base merges it over the strategy and writes run_plan.json (what will run) and assumptions.json (the ledger: precipitation used as recharge, subsurface from CONUS2, sres as published — or ELM's own). reception_brief.json and plan.json are written beside them so the standalone tools find the filenames they expect.

build_case_inputs

Reads what the build call wrote and computes nothing: ELM's case_inputs.json, PFLOTRAN's CONDITIONS_COUPLERS. The stage exists because the base's sequence has a slot for it, and on a resume it is the same read off disk. The base persists the result as 01_inputs/case_inputs.json.

build_cases — ELM only

A CIME case build takes eight to ten minutes and belongs on a compute node, so this stage is job-shaped. run_elm_ensemble submits job A — compile the reference case, clone it per column, run every column — and the manager itself submits job B with afterany (never afterok: a failed ensemble must still report). Job B runs workflow.py --finalize on the node: adopt the finished output, then extract → package → analyze. The stage returns Pending with both ids and the session ends; --resume polls check_elm_job. The manager announces the job ids before submitting; asking is the coordinator's job (the notification address, on a terminal only). PFLOTRAN declares NEEDS_CASE_BUILD = False and skips the stage: a deck is a text file, and writing it was the build.

run

Two meanings of the same slot. For ELM it collects: job A already ran the columns, so this never submits — a column succeeded if ELM wrote its history file, and the run summaries and reports are built from disk (submitting here once re-ran a landed ensemble over its own output). For PFLOTRAN it runs: run_pflotran_simulation once per deck, inline, five to ninety seconds each — one deck per call because the tool's list form runs only the first. A failed column is recorded against itself and does not stop the ensemble.

extract

Reads the model's own output format and stops: raw numbers, no interpretation. ELM: extract_run, imported ELM code, reads the history NetCDFs into 03_results/extracted.json and the rows are built from that file — one writer of one artifact. PFLOTRAN: extract_column_series writes saturation and pressure against depth per output time to the same filename, and the manager attaches each column's block to its row as profiles. The column's own setup — water table, unsaturated depth, transient or steady, forcing years, borrowed-rain distance, the server's warning — is not copied here: it is on columns.json, and the package carries it onto the row through the asserted list. What a field means (FIELD_SEMANTICS) stays on this side of the boundary, never behind a tool call.

package → experiment.json · Analyzer

experiment.json is this box's product and the Analyzer's only input: the rows with their series and their column facts (a row's warning becomes a caveat in the Analyzer's step 0), field_semantics, variable_units, the assumptions ledger, the columns, grid, boundary, domain, period, model, and the strategy check's record. RUN_SUMMARY.json sits beside it. Everything from package onward is non-fatal: by then the compute has succeeded and extraction has written its summary, and a reporting bug must not discard an ensemble that cost a queue slot. The Analyzer is called last and has its own walkthrough.

run_state.json · resume · finalize

_mark writes a line after every stage — done, failed, skipped, pending, with artifacts and job ids. --resume RUN_DIR reads it, reuses every finished stage from disk (materialize from run_plan.json, case inputs from case_inputs.json, extract from experiment.json) and advances the pending one — polling the scheduler for ELM. --finalize RUN_DIR is the tail run inside job B: it adopts the completed run without polling (the job polling would find itself) and continues from extract. Resume is opt-in; re-entering a directory without it means "do it again".

Two things not on the diagram

All three paths ran on this code on 2026-08-18. ELM site: columns.json byte-identical to the pre-refactor run. ELM conceptual: a two-level clay sweep from the request through built inputs — cold, two synthetic surface files with clay 5 and 55, one domain file. PFLOTRAN site: Naches, from a fresh request through package — 17 decks built, 17 ran, 17 read, every row carrying its profiles and its setup; dispatched by workflow.py itself, into a directory named pflotran_run_*.

What is parked. The Analyzer's frames are ELM-shaped (daily series, soil layers, depth profiles); PFLOTRAN's rows arrive with profiles and are not yet drawn. The run → analyze tail of an ELM conceptual sweep last ran on 2026-08-16. Both are the next box's business, not this one's.
