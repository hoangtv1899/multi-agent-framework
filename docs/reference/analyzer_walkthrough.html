In plain language

The Analyzer reads one finished run directory and writes one file that answers the user's question. It receives three JSON files written by earlier stages — what was asked, what was designed, and what the simulation produced — and it produces 04_analysis/analysis.json: an answer in a few sentences, a list of individual claims each pointing at the number it rests on, the figures, the constraints those claims are subject to, and what the run cost. Beside it, analysis.pptx lays the same content out as slides — a rendering of that file, never a second one.

Every report also says what kind of result it is, before it says anything else: the question was answered, or nothing survived the checks, or the evidence was too thin, or something broke. Those are four different outcomes and only one of them is a fault, so the file names which — a reader should never have to infer a crash from a missing field.

Two of the five steps call a language model. The model chooses which figures answer the question and writes the Python that draws them (step 2), and then reads the results and writes the conclusions (step 3). Everything else is ordinary code: loading the files, running the model-vs-observation comparison, executing the generated scripts in a subprocess, checking every claim against the evidence it cites, and assembling the output. No number in the final file is produced by a language model — the model names numbers, and code verifies each one appears in the data it was taken from, discarding the claim if it does not.

Scope and boundaries

The framework is four stages in sequence — Reception, Planner, Experiment Manager, Analyzer. Each writes one boundary artifact: a JSON file that is the entire interface to the next stage. The Analyzer is the fourth.

The Analyzer ownsThe Analyzer does not own
Loading the three boundary artifacts and splitting them into question, evidence and constraints Fetching observations. Reception fetches them once, when the simulated period is fixed, and stores them in reception.json. The Analyzer reads that copy and never re-fetches.
Deciding which comparisons and figures the question needs Reading native simulation output. No NetCDF, no HDF5, no PFLOTRAN .h5. A backend extractor turns those into 03_results/extracted.json.
Executing generated analysis code and validating its output Knowing what an ELM variable means. The model-vs-observation comparison lives in the ELM server's compare package, because it needs to know that H2OSNO is snow and how deep ELM's soil column goes.
Auditing the interpretation and writing analysis.json Deciding whether the run succeeded. That is the Experiment Manager's judgement. A run where every column finished is a manager success even if every column drains twice its precipitation.

Is analysis.json the single authoritative output?

Yes, and it is written in exactly one place. Searching the repository, the only writer is step4_report.write(); run_layout.py registers analysis.json as the Analyzer's boundary artifact, and ExperimentManagerBase records its path under artifacts.analysis_report without opening it. No later stage reads it, rewrites it, or passes it to a model.

Nuance worth knowing. Re-running the Analyzer over the same directory overwrites analysis.json, and the intermediate files (comparison.json, investigation.json, interpretation.json) are overwritten each round as well. The file is authoritative for one execution; it is not a versioned history. Nothing enforces that a second execution agrees with the first.

  • language-model call

extracted.json is drawn above the Analyzer because it is not the Analyzer's input. The backend extractor writes it from the native simulation output; the Experiment Manager reads it, builds one row per column, joins the sampling metadata on, and writes those rows into experiment.json. By the time the Analyzer runs, everything it needs is inside experiment.json, which is why the Analyzer never opens extracted.json and works identically on an archived study whose simulation output has been purged.

plan, data, caveats — what each is for

plan is the question. The user's request, the basin, the simulated years, the sampling design, the feasibility verdict. A later step reads it to know what is being asked. It is never a source of numbers. A figure count or a column count that appears only in plan is a statement of intent — what was designed — and the run may not have delivered it.

data is the evidence. The per-column rows with their daily series and metrics, the ensemble-level blocks, the units, and the observations Reception fetched. This is the only place a reported number may come from, and step 3's audit enforces it: a value a claim declares must appear in the finding it cites, and every finding is computed from data.

caveats are the limits. Not intent, not evidence — they say what the evidence is not allowed to support. Every caveat is a five-field record, which is what makes it checkable:

{"id":         "limitation_structural_2",
 "severity":   "blocking",
 "statement":  "Local runoff generation on a 1 m² column, not routed discharge…",
 "applies_to": "any comparison against a stream gauge",
 "source":     "experiment.json:limitations"}

Severity is what the caveat does, not how serious it sounds. blocking — the claim must not be made, or must carry the id; this is the only severity the audit enforces. qualify and context travel to the report and constrain nothing mechanically.

applies_to is the field the audit matches against, not the statement. Scope wording that names the subject ("recharge, drainage and any water-table claim") works; wording that names the machinery ("the water_table comparison") does not.

Why df, soil and prof are three frames

Each holds a different combination of axes, and merging them would mean dropping one.

framebuilt byone row iscolumns
dfctx.series()one value per date per column date · entity · variable · value · units · source
soilctx.soil()one value per date per layer per column adds layer · depth_m · thickness_m · depth_top_m · depth_bottom_m
profctx.profiles()one value per output time per depth entity · time_y · depth_m · variable · value · units · source

An axis mismatch, in one example. A 15-layer column simulated for a year has 352 dates and 5,280 SOILLIQ values — one per day per layer. Pairing those two lists directly does not fail; it stops at the shorter one, producing 352 values that are actually the first 23 days of the soil profile, labelled with a year of dates. Every check passes: the column exists, the dates are real, the units are right. series() therefore refuses any variable whose counts disagree, and records the reason in series_withheld, which step 2's brief prints. A depth-resolved variable is not an error — it is routed to soil, where the layer axis survives.

A mean over soil must be weighted by thickness_m. ELM's layers span 1.75 cm to 13.85 m, so an unweighted mean reports the bedrock. Documented in the prompt and the module docstring; not mechanically enforced.

Between 0 and 1 — the preflight gate

Not a step. One question asked once, after the context is built and before anything is spent on it: is there anything here to analyse?

blocked is set in exactly two cases, both about the run rather than the science: the run packaged no columns at all, or no column produced a series, a soil layer or a depth profile — meaning every script step 2 could write would fail on the same missing frame. Anything subtler than that is not the gate's business.

Why it exists. Before it, a run whose columns carried no usable series still reached step 2, spent a model call on five figure specifications, and learned the frames were empty one subprocess at a time. One earlier study spent both rounds and four model calls to establish that the field it needed was in no frame. The information was available the moment step 0 returned.

The gate does not judge the science. It reports what the packaged run contains. Whether the contents answer the user's question is step 3's to say, and a run that passes preflight can still end at insufficient_evidence for entirely different reasons.

Three consumers share the one computation. The gate uses blocked; step 2's variable filter uses variables to refuse a proposed figure whose variables are in no frame; step 2's brief prints withheld so the model proposes what exists. feasibility and unmet_plan_targets carry the Planner's own verdict and planned_vs_actual()'s check of it into the same record — both were computed and read by nothing before this gate was written.

Fails open. preflight_of() catches any exception and returns an empty dict, so a fault in the gate cannot block a run that would otherwise have worked. The one consequence is that step 2's variable filter turns itself off when the inventory is empty — can_filter = bool(have) — because an empty inventory means not measured, not nothing exists, and treating those as the same thing once refused every figure in a healthy run.

When a comparison cannot be made

It returns a record saying so, and that record is still a finding. "No gauge inside the basin had daily records that year" is a fact about the basin; reporting it as an empty comparison would make it look like a failed query. The comparison never returns a verdict — "bias = −85.9 mm" is in the record, "the model underestimates snow" is not. comparison["caveats"] is present and always empty: archived runs written before this step stopped deriving caveats have real entries there, and dropping the key would make old and new records differently shaped.

What the model receives

context_brief(ctx, step1) builds it deterministically, so it can be asserted on in a test without an API call. It contains: the user's question; the run's shape; a catalogue of the variables actually present in the frames with the units they carry in the frame; the derived metrics and what each is computed from; which variables were withheld and why; the blocking caveats quoted with their applies_to scope; and step 1's measurements rendered by format_comparison().

The units come from the frame, not from ctx.data["variable_units"]. Both maps are correct about their own subject — the second describes the raw ELM variable (QOVER in mm/s) while the frame holds daily values already converted to mm/day. Printing the raw map under a heading about the frame is what once led to a plot of 1.1 × 10⁶ mm/yr of runoff.

What it produces, and how that is executed

The model returns JSON, not prose: reasoning, notes, and a list of figure specifications each with id, question, why, scale, variables and code — a Python snippet. The model produces no numbers. Every value in every finding is computed by pandas inside the executed script. That is what makes step 3's audit possible: a claim can be checked against the data it came from only if the data was computed by something other than the thing making the claim.

The execution boundary — what the generated code can actually do

This is the one place in the framework where model-authored code runs. It is worth being exact about the trust model.

Resource ceilings_limits(), applied between fork and exec: 8 GB address space, 300 CPU seconds, 512 MB per file, no core dump. Each turns a runaway into a clean non-zero exit the caller reports as a caveat.

Still not a sandboxNetwork access is not blocked — that needs namespaces or root. The proxy variables point at a dead port, which stops the libraries that honour them and nothing else; the real protection is that a script reaching the network has no credentials to authenticate with. Filesystem reads outside the run directory are not blocked, and the AST check is trivially bypassed by anything trying to. The threat model is carelessness, not malice.

How numeric output is validated

The script must assign a dict named result. Six guards run in order, and each returns a reason rather than raising:

Guard 5 is the reason this file exists. A filter that matches nothing, a merge on a misaligned key, or a .dropna() that removes everything all return a clean, plausible, empty answer. Requiring the script to state how many data points its claim rests on turns that from a silent gap into a recorded failure.

Reproducibility

Each accepted figure leaves three things in 04_analysis/: the PNG, the complete executable script (preamble that loads the payload, the generated body, postamble that writes the result) and the finding in investigation.json carrying the numbers, n, a script_sha256 of the generated body, and paths to both. A reviewer can open the .py and run it — the preamble uses the pickled payload while it exists and otherwise rebuilds it from the run directory, taking the same path step 0 takes. The hash covers the generated body rather than the assembled file, because the preamble embeds temporary paths that differ between two runs of the same analysis.

The exchange, verbatim

script_runner.save_exchange() writes what the model was shown and what it said, unparsed, as step2_round<n>_prompt.txt and step2_round<n>_reply.txt. Step 3 does the same under step3_. Neither survived before; the reply came back from propose() as raw and was dropped once parsed. Two questions about a finished run therefore had no answer:

  • "Five figures were proposed and four appeared — what happened to the fifth?" The four that parsed are on record. One mangled on the way in left no trace it was ever proposed.
  • "Did the parser change what the model meant?" _parse() repairs replies that are not quite valid JSON — escaping raw newlines inside generated Python, stripping comments. Usually right. When it is wrong, the original was already gone.

The prompt is kept for a specific reason, not for symmetry. The worst defect this pipeline has had was a silent 700-character cap on each finding: the model was shown a fifth of a result and told to quote from it exactly, and the audit then struck nine of fourteen true claims. Nobody could see that, because nobody could see what had been sent.

Saving both is also what makes an end-to-end test possible without calling a model — a recorded reply replays identically and for nothing. tools/show_prompt.py --run-dir <dir> --step 2|3|both rebuilds the same prompts read-only, without running a comparison or spending a call, for anyone who wants to read one before a run rather than after.

Never fatal: a run that produced figures is not lost because a log could not be written.

The plan document

render_plan_md() writes investigation_plan.md after the figures have run, so each step carries its outcome rather than its intention. It is rendered from the same structured record as investigation.json and so cannot disagree with it; the only model-authored prose in it is reasoning and each figure's why, both attributed. Step 3 reads this file.

What the interpreter receives

review_brief() assembles, in this order: the user's question; the blocking caveats with their scopes; step 2's plan document in full (capped at PLAN_CAP = 8000 characters); then one FINDINGS: list holding step 2's findings and step 1's comparison findings in the same shape; then any figures that failed. The figures themselves are attached as images alongside the text.

The one-list rule is structural: whatever the audit will accept is shown in one shape, under the id that has to be named. Each finding's result is rendered whole if it fits RESULT_CAP = 6000 characters; when it must cut, it says so and forbids quoting numbers from that finding.

{"id":         "annual_water_budget_by_elevation",   # what a claim must cite

blocked_by is filled by _blocked_by(), which matches a figure's variables against each blocking caveat's applies_to field — case-sensitively, on word boundaries, and against applies_to only. Case matters because ELM variable names collide with ordinary English: matching SNOW case-insensitively tagged every precipitation figure with a snow caveat. Step 1's findings use the same schema with ids of the form compare_<observable>.

What the audit checks — the three rules, by name

Each is a function, applied in this order; the first to object wins, and a claim that passes all three is kept. A struck claim carries struck_by — one of AUDIT_RULES — beside the prose reason, so strikes can be counted per rule without parsing English.

rulefunctionwhat it requires provesdoes not prove
cites rule_cites() finding_id names a finding that exists there is evidence behind the sentence, and it can be located that the finding supports the sentence
declared_values rule_declared_values() every entry of the claim's values list appears in that finding's result no fabricated measurement survives that the number means what the sentence says — a value used with the wrong variable, unit, period or sign passes
respects rule_respects() a claim whose own text is about a blocking caveat's subject carries that caveat's id a claim inside a forbidden scope acknowledges it explicitly that the acknowledgement is meaningful — carrying the id satisfies the rule

The names used to exist only in prose. A reviewer sent to find the function implementing no_new found three anonymous blocks inside audit() and no such name anywhere in the source. They are functions now, and no_new is gone as a name because it described the rule this one replaced — a scan of the sentence for any number not in the finding, which needed six exemptions in a row and still struck correct claims.

Three deliberate exemptions widen "appears in that finding": run_facts(ctx) allows the column count and the simulated years, which are facts of record; every finding's own n is allowed; and anything matching _YEARLIKE passes.

There is no final schema validation of analysis.json. It is written with json.dumps and nothing checks its shape on the way out. Intended but not enforced.

What the audit does not check

  • Numbers written in prose. Only the claim's declared values list is audited. A number that appears in the sentence but not in values is not checked.
  • Whether the sentence is true. The audit can stop a fabricated measurement. It cannot stop a false statement built out of real numbers.
  • Whether the right number was used. A value that is genuinely in the cited finding passes even if the claim attaches it to the wrong variable, unit, period, location or sign.
  • Whether the figure supports the claim. The images are shown to the model; nothing compares a claim to the pixels.
  • Non-blocking caveats. qualify and context caveats travel to the report and bind nothing.
  • The answer paragraph. Only claims are audited — see step 4.

What happens to rejected claims

They are not deleted. Each moves to struck with a struck_because sentence and a struck_by naming which of the three rules fired, and step 4 carries them into analysis.json under withheld. A claim that was made and rejected is evidence about the run.

"Insufficient, once"

investigate_and_interpret() loops at most MAX_ROUNDS = 2 times. Each pass is a full new investigation, not a retry of the interpretation: step 2 is called again with step 3's feedback, proposes a revised figure set, and runs it; then step 3 interprets afresh. So a second round costs one step-2 model call, one subprocess per figure, and one step-3 model call.

The loop stops early on "sufficient", and also on "insufficient" with no actionable feedback — there is nothing to send back. If round 2 is still insufficient, that verdict stands and is reported. "This experiment cannot answer the question" is a result, not a failure, and step 4 files it as insufficient_evidence rather than as a malfunction.

What each round records, including when it went backwards

Every pass appends one entry to rounds: round · n_proposed · n_succeeded · verdict · n_claims · n_struck · n_claims_kept · feedback · finding_ids. From round 2 on, two more appear when they apply:

  • findings_dropped_from_previous_round — ids the earlier round produced that this one no longer has. A revision is allowed to replace evidence, but a reader comparing the two rounds should not have to diff the id lists by hand to notice.
  • regressed — a sentence recording that this round kept fewer claims than the last. It is not corrected: the reviewer judged this round's evidence and that judgement stands. It is recorded because an extra round that cost claims rather than earning them is a fact about the run, and investigate_and_interpret() surfaces the list as regressed_rounds.

How audited findings become the output

build() is pure: it computes and concludes nothing. Step 2 computed, step 3 concluded, and step 3's audit already decided which claims survived. Each kept claim is emitted with the finding it cites, the values it declared, its caveat ids, its n, and the paths to its figure and script — so every sentence in the file carries its own provenance.

The four statuses

Every report carries a status before it carries an answer. A reader — or a dashboard, or a mailer — that branches on verdict alone cannot tell a crash from a conclusion, because a crash has no verdict at all: the field is simply absent, and absent read as "inconclusive" files a malfunction as a scientific judgement.

statusconstantmeansset when
supportedSUPPORTED it ran, concluded, and at least one claim survived the audit no step failed, verdict is sufficient, and n_claims > 0
no_supported_claimsNO_CLAIMS it concluded, and the audit kept nothing as above with n_claims == 0
insufficient_evidenceINSUFFICIENT it looked, and judged the evidence too thin. A result, not a malfunction. preflight blocked the run, or the interpreter's final verdict was not sufficient
analysis_failedFAILED a stage did not run to completion any entry in steps is False, or there is no verdict and no explanation

Order matters, and the preflight check comes first. A blocked run marks steps 1–3 False because they did not run — but they did not run because the run was inspected and found to hold nothing, which is a finding about the evidence. Checking preflight before steps is what stops "we looked, and there is nothing here" from being filed as "we broke".

When no steps record is passed at all, any run without a verdict is reported as analysis_failed — the safe direction to be wrong in, since it never dresses a crash as a judgement.

The review brief proposed a fifth status, partially_supported. It is not implemented: nothing in the pipeline currently distinguishes a partial answer from a complete one, and a status no code can assign is a status that would always read as absent. no_supported_claims occupies the nearby ground — the run concluded, but nothing survived.

What the file records about the run itself

provenance carries what the coordinator knew and used to throw away at the boundary: steps and failed_steps (which stages completed); preflight (what the run contained, decided before any model was asked — on a blocked run this is the entire account of why nothing was investigated); rounds and stopped_because; investigation_plan, the path to the Markdown plan step 2 wrote and step 3 reviewed against; and audit, step 3's own tally. A reader opening the directory six months later gets the same account the terminal gave on the night.

cost.llm reports measured alongside the totals, and splits the Analyzer's own spend out under analyzer using ANALYZER_LABELS — the two client labels step2_investigate and step3_interpret. unattributed is what is left after every label is subtracted, computed by summing the labelled calls rather than by asking for a filtered total: usage_totals(None) means no filter, so the earlier version returned the grand total and reported every run as entirely unattributed.

Can unaudited text enter the output?

Yes, in one field, and it is worth knowing which. answer is the model's 2–4 sentence summary, copied verbatim from step 3 and not audited — the audit operates on claims, not on answer. In practice the answer restates the claims, but nothing enforces that. Everything else in the file is either an audited claim, a struck claim with its reason, a caveat record, a figure path, or a measured cost.

The slide deck — a second rendering, not a second report

write() writes analysis.json first and always, then calls step4_slides.build(report, out_dir) with the same dict and returns the JSON's path — because that is the boundary artifact every caller means by "the report". A failure in the presentation layer therefore cannot cost the run its result.

step4_slides.py reads the report and lays it out. Nothing there computes, rounds, re-words or omits a number. A deck that disagreed with the file it came from would be the worst artifact in the run, because the deck is what gets presented while the file is what gets checked. Concretely: no claim appears without the finding id it rests on, struck claims travel with struck_by and the reason, caveats are quoted rather than summarised, and a run whose status is not supported says so on the title slide instead of opening with an answer it has not earned.

python-pptx is optional. It is installed in the ideas environment, but a run without it must still finish — build() returns None and prints why, and analysis.json is unaffected.

How it is presented

Analyzer.run() prints step4_report.summary(report) to the terminal — verdict, claim counts, rounds and cost — and returns a status dict containing the report's path. The status is what the Experiment Manager sees. Nothing downstream can replace or rewrite analysis.json; the only way it changes is a fresh Analyzer execution overwriting it.

A submitted run has no report yet, and says so. When the Experiment Manager queues an ensemble instead of running it, workflow.py prints how many columns were queued and names both scheduler jobs — the one that builds and runs, and the dependent one that runs workflow.py --finalize afterwards. It does not print an execution tally, a skipped-report line, or a completion tick, because at that moment nothing has run: a run reporting 0/19 succeeded before its jobs started reads as nineteen failures.

Tracing a number backwards

Every number in analysis.json reaches disk by one of two paths, and they never merge.

A simulation value

  1. claims[i].values[j] in analysis.json
  2. → claims[i].finding_id names a finding
  3. → that finding's result in investigation.json, which contains the value (the audit guarantees this)
  4. → the finding's script — the exact Python that computed it
  5. → the script read df / soil / prof, built by ctx.series() etc.
  6. → from experiment.json → columns[*].variables[var].daily
  7. → written by the Experiment Manager from 03_results/extracted.json
  8. → written by the backend extractor from the native simulation output

An observation value

  1. claims[i].values[j] in analysis.json
  2. → finding_id is compare_<observable>
  3. → that finding's result in comparison.json
  4. → computed by mcp/elm-mcp/src/compare/<observable>.py
  5. → which read the stations out of reception.json
  6. → fetched once by Reception from the external service (USGS, SNOTEL, AmeriFlux) when the period was fixed

The Analyzer never re-fetches. A second fetch can disagree with the first, and then the run's own record is not what was compared against.

The two paths are distinguishable in the final file without following them: an observation number lives in a compare_* finding, a simulation number in a step-2 finding. Confusing the two is the single commonest way a true sentence gets struck, which is why step 3's prompt says so explicitly.

Glossary

boundary artifact
The single JSON file that is one stage's entire interface to the next — reception.json, strategy.json, experiment.json, analysis.json.
context
The in-memory AnalysisContext that step 0 builds, holding plan, data and caveats. Never written to disk.
frame
A tidy pandas DataFrame the generated scripts read. There are three — df (daily), soil (daily per layer) and prof (depth profiles) — because each holds a different combination of axes.
axis
One dimension a value varies along: time, depth, layer, or column. An "axis mismatch" is pairing two lists that vary along different axes, which produces a plausible-looking frame of mislabelled numbers.
finding
One computed result with an id, the question it answers, the numbers it produced, how many data points those rest on (n), and the figure and script that made it. The only thing a claim may cite.
caveat
A five-field record stating a limit on what the evidence may support: id, severity, statement, applies_to, source.
audit
The pure function in step 3 that checks each claim against the finding it cites and removes the ones that do not hold up. No model is involved. It audits provenance — where a number came from — not whether the sentence around it interprets that number correctly.
candidate claim
A sentence the interpreter proposes, before the audit has judged it. It names a finding_id, the values it declares, and the caveat ids it carries.
audited claim
A candidate claim that survived all three rules. Only these reach analysis.json's claims; the rest go to withheld with struck_by and the reason.
preflight
One question asked between step 0 and step 1: does this run hold anything to analyse? It reports what the packaged run contains — never whether the contents answer the question — and when it finds nothing it skips steps 1–3 before any model is called.
status
What kind of result a report is, distinct from what it says: supported, no_supported_claims, insufficient_evidence or analysis_failed. It exists because a crash has no verdict at all, and an absent verdict read as "inconclusive" files a malfunction as a judgement.
floor
A key list naming the minimum a producer must supply. Extra keys are allowed; missing ones raise.
whitelist
A key list that selects what crosses a boundary. Here, one that also names what it deliberately leaves, so an unlisted key can raise.
pass-through contract
A key list that documents the expected keys but copies everything, so nothing can be dropped by it.
identity
The fields that say which column a row is — its name, place, elevation, forcing period, and whether it was pinned to a station — as opposed to what the column measured.
backend-neutral artifact
A file whose shape does not depend on which simulator produced it. experiment.json is one, which is why the same Analyzer reads an ELM run and a PFLOTRAN run.
pinned column
A sampled column placed deliberately at an observation station so the two can be compared, rather than chosen by the elevation-band design.
Appendix A

Design history

Why the current shape is the shape it is. None of this is needed to use the Analyzer; it is here because each item explains a constraint that would otherwise look arbitrary.

The Analyzer was inside the Experiment Manager

The manager both ran the simulation and judged it, so "the experiment succeeded" and "the experiment showed something" were decided by the same code. They are different questions. A run whose columns all completed is a manager success even when every column drains twice its precipitation.

The comparison moved into the ELM server (2026-08-12)

Step 1 used to own four modules — roughly 1,400 lines that knew H2OSNO from ZWT, what a snow pillow is sited for, and how deep ELM's soil column goes. None of that is backend-neutral, and the Analyzer is the one box that must be. It now lives in mcp/elm-mcp/src/compare/, and step 1 is the caller plus the judgement about what those measurements may support.

A registry replaced the hardcoded import shortly after: the file imported ELM's package whatever the run was, so a PFLOTRAN study would have asked ELM's modules for H2OSNO, found nothing, and written four empty records as though the comparison had been made. "We could not look" reported as "there is nothing there" is the exact failure this box exists to avoid.

Step 1 stopped deriving caveats (2026-08-13)

It used to add eight per run. Each one restated a measurement the summary already carried — below_active_soil, onset_censored_columns, gauges_exceeding_modelled_domain — so the step was measuring and ruling on its own measurement, and the interpreter's brief was 24% caveats against 43% measurements. Understanding what the scope permits is the interpreter's job. Caveats now have one producer: step 0, reading experiment.json.

The citation strike, and what it turned out to be

On the 2026-08-13 verification runs the audit struck 9 of 14 claims. Every struck value was a real measurement from that run, cited under the wrong id — so the audit was right fourteen times out of fourteen and the fault was upstream. Two causes, both in how the evidence was displayed:

  • Step 1's findings were rendered as a prose block while step 2's were listed with ids, though the audit accepts both. A model writing about snow cited the step-2 finding whose subject matched while quoting numbers that lived in compare_swe. 8 of 15 struck values. Fixed by rendering both in one FINDINGS: list.
  • A silent 700-character cap on each result. One finding held 324 numbers and 292 were behind the cut; 5 of 10 findings were truncated. The model was shown a fifth of a result and told to quote from it exactly. Fixed by raising the cap to 6,000 and saying so when it does cut.

Re-running step 3 alone over the same findings, so only the prompt differed: Naches 3 kept / 5 struck → 11 / 0; Brandywine 2 / 4 → 9 / 1. The survivor was a genuine respects strike.

The audit's own worst false positive

_blocked_by tags a figure with every caveat scoped to any variable it used, so a five-variable figure inherits five caveats. Enforcing all of them on every claim struck "no observational validation of the water table is possible" for not carrying a caveat scoped to runoff. required_caveats() now narrows the figure's candidates to the ones the claim's own text is actually about.

An earlier version matched a caveat's full statement as well as its scope, and struck every claim in a live run: one caveat scoped to the water table mentions QDRAI in passing, so every drainage figure inherited it. An audit that strikes everything is indistinguishable from one that is broken.

The recurring failure this whole design is arranged against

A null that means "not computed" rendering identically to one that means "computed as nothing." Four instances, all real:

  • soil_attribution filtered on a key the extraction never populated, returned {}, and its figure simply did not appear — for the entire history of a study, with nothing recording that a planned analysis produced nothing. This is why script_runner requires an n.
  • A capability probe tested row["soil"]["clay_max_pct"], null on 100% of columns across every run ever packaged, while soil_profile beside it was complete. The soil figures were never offered, on any run.
  • SOILLIQ's 5,280 layer-values were zipped against 352 dates, silently producing 23 days of soil profile relabelled as a year. It surfaced only when a reviewer looked at the figure and said a soil-water trace cannot collapse and rebound every fortnight — the fortnight being the 15 layers, cycling.
  • A stale variable name after a refactor raised NameError, which a bare except Exception swallowed and reported as "limitations payload unavailable" — a run with no limitations rather than code that did not run. Since step 1 stopped deriving caveats that same morning, that payload is the only source of anything blocking.
