IDEAS · the fourth box

Analyzer Walkthrough

One diagram, and a few sentences on each box in it. The Analyzer turns a packaged run — experiment.json, with reception.json and strategy.json beside it — into an answer a reader can trust: it compares the model to what was observed, has a language model propose figures and write the code, has it interpret them, and then audits every claim in code before writing the report. It reads three files, opens no server, and knows no model: what only a model knows lives beside that model's server and is imported by name.

The boxes, top to bottom

step 0 · context

The only step that opens a file. It reads the three boundary files and splits experiment.json through a declared key list: eleven keys become data — the only place a reported number may come from — and the rest say where they went (plan, or the caveats); a key on neither list raises. Caveats are uniform records with a severity — blocking (the claim may not be made), qualify (made with this attached), context — from seven sources: the limitations catalogue, the assumptions ledger (both models' shapes), a bbox-not-watershed sample, an untrimmed spin-up, a row's own warning (one caveat per distinct sentence, naming the columns), the strategy check's corrections, and any observation fetch that failed. Three tidy frames are built once from the rows — series (daily), soil (layers through time), profiles (depth × output time) — and a frame the run does not have is None, which is the honest answer.

A coupled run needs nothing added here. The seven coupling facts the upstream model left on each column — coupled_from, coupling_variable, the water table it was started at, what was actually written into its initial state and why, the prior value and the difference between them — ride the same asserted key list every other column fact rides, and land in data as ordinary per-column numbers. That is what lets the Analyzer notice, unprompted, that a run began at another model's answer and ask whether it stayed there.

gate · preflight

Before anything is spent: is there a frame at all, and what does it hold? A run whose columns carry no usable series used to reach step 2, pay for five figure proposals, and discover the absence one subprocess at a time. Now the gate answers it from the frames — and if nothing is there, the report is still written, saying so: “this run cannot be investigated, and here is what it contains” is a result. The gate fails open: a fault in preflight itself must not stop a run that would otherwise work.

step 1 · compare

Code, no verdicts. The run's model chooses its comparison package — mcp/elm-mcp/src/compare/ (snow, water table, streamflow, ET, a map) or mcp/pflotran-mcp/compare/ (the water table: the depth where the solved pressure crosses atmospheric, found bottom-up, and the CONUS2 depth the column was given, against wells) — loaded by path from beside its server. Everything model-blind is the framework's, in compare_common: reading reception's observations, pairing a station to a column by the sampler's pin first and by distance second, metrics, figures, and the driver that compares, draws, writes comparison.json and summarises. “bias = −0.84 m” is a measurement; “the model underestimates” is not said. A conceptual sweep, and a model with no package, are skipped — recorded as such, never reported as an empty comparison. Each observable becomes one finding the interpreter may cite.

step 2 · investigate

LLM One call per round. The brief names the run's model, states the question and the planner's goals, catalogues the frames and every declared field — where it lives: a variable of prof, an axis, an input on the row, a metric — lists the caveats and step 1's summary. The task asks for at most five figures at two scales, each as Python that draws from the bound frames and sets a result dict with the numbers plotted and an n. Each script runs in a subprocess with a timeout, resource ceilings and an import allowlist; it must save the PNG and report n ≥ 3 or it is rejected. A failed figure becomes a context caveat, not a silent gap; blocking caveats scoped to a figure's variables travel with it as blocked_by. What was sent and what came back are saved verbatim beside the run.

step 3 · interpret, then the audit

LLM One call per round, with the figures attached as images: the findings with their numbers, the plan, the blocking caveats, and a task that demands claims naming the finding they rest on and the values they use. Then code audits the judgement, three rules in order and the first objection strikes: cites — the finding exists; declared_values — every number in the claim is in that finding (or is a run fact: column count, years); respects — a blocking caveat whose subject the claim's own words touch is honoured. A struck claim is kept with the rule that struck it, never dropped. The audit stops a fabricated measurement; it does not catch a true number attached to the wrong variable, and says so.

gate · verdict, and the one loop

The interpretation ends with sufficient or insufficient and, when insufficient, feedback. Feedback goes back to step 2 for one more round of figures — at most two rounds — and the record says which findings were dropped, which claims regressed, and what the second round was answering. An unparseable verdict is insufficient.

step 4 · report and slides

Code that computes nothing and concludes nothing. It says what kind of result this is before what it says — supported, no_supported_claims, insufficient_evidence, analysis_failed — then the answer, the claims step 3 kept, the withheld ones with their rule, every caveat, the figures, provenance (which steps ran, the preflight), and cost: language-model spend attributed by step, and compute from the run summary when it exists. analysis.pptx is a second rendering of the same dict — it may not round, reword or omit a number.

Two things not on the diagram

It runs on both models, proven 2026-08-18. The same five steps read a PFLOTRAN run through its report: step 1 paired a well to a column (a synthetic one — Naches has no recorder well; see tools/synthetic_well.py) and, without one, still returned where the water table sits and how far it moved; step 2 drew from the profiles frame; step 3 kept the caveat that eight of seventeen columns began saturated; the report named no ELM quantity. ELM's comparison, re-run through the shared half on two archived runs, gave every number identical.

It reads a coupled run without being told, proven 2026-08-19. Handed an ELM run started at PFLOTRAN's solved water tables, the Analyzer found the coupling facts among the ordinary column facts and made the comparison the coupling exists for: it drew the drift away from each imposed water table over the year, reported that the columns held within about a metre, and returned sufficient. Nothing in the five steps knows the word "coupling" — the numbers were on the rows, and that was enough.

What still leans on one model. Step 3's caveat scoping recognises a variable by its being UPPERCASE (ELM's names); PFLOTRAN's lower-case names are scoped by words instead, which works but is a heuristic. Step 4 asks the scheduler for the ensemble's wall time through a job id only ELM records; a PFLOTRAN run, and an ELM ensemble that ran inside an existing allocation, have no job to ask about and say so — the runtimes then come from the run summary, or from experiment.json when the Analyzer runs before the summary is written, which on a live run it always does.
