How the Analyzer reaches a conclusion

Five steps over one finished run directory. Two of them call a model; the other three are code, and the code is what decides whether the model's sentences survive.

The shape

Where the numbers come from, and where they are allowed to go

Every step takes the context plus what earlier steps returned, and returns data. Step 0 is the only step that opens a boundary file — that is what lets any later step be re-run alone against an archived study, months after the compute is gone.

Step by step

What each step is allowed to do

experiment.json returnsplan · data · caveats

Context — split three ways, on purpose

plan is the question and is never a source of results. data is the evidence and is the only place a reported number may come from. caveats are neither: they bound what the evidence is allowed to support.

It also builds the frames the figure step works in, one per axis combination: df is one value per date, soil is one value per day per layer with each layer's own thickness, and prof is PFLOTRAN's yearly snapshots by depth. Forcing a layered field into the daily frame means dropping an axis, and dropping the layer axis is the bug this split was built after.

A variable whose values do not number the same as its dates is withheld and named rather than zipped. That check is what stopped H2OSOI entering the frame as the first three weeks of the soil profile wearing a year of dates.

Since 2026-08-13 the rows in experiment.json are themselves built from 03_results/extracted.json rather than in the same pass that opened the NetCDF. So a number in the report traces back through step 0 to a file that outlives the scratch filesystem the model wrote to — which is the property the rest of this page depends on and did not previously have.

step 1 readsctx only writescomparison.json
4 figures + map caveatsnone

Compare — the server measures, this step makes it citable

The measuring belongs to the model's own server, chosen from the run rather than assumed: ELM's compare package handles swe, water_table, streamflow and et — each matched then compared, returning bias, RMSE, NSE, KGE and the diagnostics about the matching itself. It offers no verdict, deliberately. A backend with no comparison registered gets told so; it does not get ELM's.

It turns those numbers into findings step 3 may cite, one per observable, carrying its figure. Without them a sentence about an observation had nothing to cite and the audit struck it — the interpreter could describe the model and was forbidden to say how it compared.

It derives no caveats, as of 2026-08-13. It used to add eight, including four blocking. Each restated as a verdict a measurement the summary already carried — below_active_soil, onset_censored_columns, gauges_exceeding_modelled_domain — so the step was measuring and ruling on the measurement, which is the one thing its own docstring says it does not do. Understanding what the scope and the model choice permit belongs to whoever interprets.

Streamflow matches nothing. A gauge measures an area, so the ensemble mean stands against each gauge as context, and no metric between them scores the model.

step 2 readsctx + step 1 writesinvestigation.json
up to 5 figures driven bystep 3
1 model call per round · then N subprocesses

Investigate — the model decides, the machine computes

This step is where the arithmetic happens. The model is shown the question, the variable catalogue, the caveats and what the comparison measured; it returns figure specs with Python. Step 2 then runs each script itself, in its own subprocess through script_runner — a real timeout and crash isolation, which exec() in-process cannot give. Each script must assign a result dict and an n; a result with n under 3 is rejected.

So two different actors work in this one step, and separating them is the whole point: the model produces no number and the machine makes no judgement. That is what lets step 3 check a claim against the data it came from. Nothing here concludes anything.

There is no step-2 call in Analyzer.run(). Step 3 owns the loop — investigate_and_interpret runs step 2, judges it, and may run it once more. The two are one bounded exchange rather than two stages, because the thing being bounded is how many times the reviewer may ask for more.

step 3 readsctx + steps 1, 2 writesinterpretation.json
1 model call per round · sees the figures

Interpret — the model judges, code audits the judgement

It computes nothing of its own: a number with no finding behind it cannot be checked against anything. It looks at the figures as images, which is how it caught a soil-water trace that collapsed to zero every fortnight — the fortnight being fifteen soil layers, cycling.

Then it returns a verdict. Insufficient sends step 2 back once, with specific feedback; the second round's verdict stands whatever it says.

step 4 readseverything writesanalysis.json

Report — assemble, recompute nothing

Each surviving claim carries its evidence: the figure a reader can look at and the script that produced the numbers. Struck claims travel too, with the reason — deleting them would make the report look like the reviewer never disagreed with anything.

It also records what the answer cost: LLM tokens and seconds per step, the ensemble's compute, and how many rounds ran and why it stopped. An answer that took one call and one that took six read the same otherwise.

As of 2026-08-13 this is the only report the framework produces. Until that morning a second interpreter ran after this one on the chat path and printed its own answer instead — over a payload with the comparison, the caveats and the figures stripped out. Everything on this page describes the pipeline; what a user actually read was the other thing. The coordinator now prints analysis.json.

Where it sits

What the Analyzer is not allowed to do

Three of these were enforced by deleting code rather than by adding a rule, which is the only enforcement that cannot be argued around later.

not thisbecause
Reach outside for data Reception is the only component that does. Step 1 compares against observations already fetched and persisted in reception.json; refreshing them means re-running reception.
Read the model's output format The ELM server reads history files and publishes extracted.json. The Analyzer reads the package, and works identically over a PFLOTRAN run.
Take a second opinion One interpreter, whose claims the audit can strike. Two produce two answers and no way to choose between them.
Let the server pick the subject The extractor measured; it does not also nominate which variables matter. A focus_variables block that did exactly that was deleted with the second interpreter it was written for.
The audit

Three mechanical checks, and what they caught

These run in code, with no model in the loop, because a prompt cannot be verified after the fact. This is where every caveat raised upstream finally binds.

What the audit caught, and what it revealed

On the 2026-08-13 verification runs the audit struck 9 of 14 claims. Every struck value turned out to be a real measurement from that run, cited under the wrong id — so the audit was right fourteen times out of fourteen, and the failure was upstream of it.

"Against the two co-located SNOTEL pillows, modelled SWE is biased low but tracks the seasonal shape…" Struck: declared −85.8531, 196.9291, 0.2867 and 0.4612 while citing swe_snotel_validation. Those four numbers live in compare_swe. The claim named the finding whose subject matched, not the one its numbers came from.

Tracing all 15 struck values: 8 sat in a compare_* finding, 6 in a different step-2 finding, 1 nowhere. Two causes, both in how the evidence was shown rather than in the rule:

causemeasuredfixed by
Step 1's findings were rendered as a prose block while step 2's were listed with ids — though the audit accepts both. 8 of 15 values one uniform FINDINGS: list holding exactly what the audit accepts. The verification asserts ids-shown = ids-accepted.
A silent 700-character cap on each result. The model was shown a fifth of a finding and told to quote from it exactly. partition_fractions_vs_elevation held 324 numbers; 292 were behind the cut. 5 of 10 findings truncated. cap raised to 6,000 — nothing measured is cut — and when it does cut it says so and forbids quoting from that finding.

Re-running step 3 alone over the same step-2 findings, so only the prompt differed: Naches 3 kept / 5 struck → 11 kept / 0 struck; Brandywine 2 / 4 → 9 / 1. The one survivor is a respects strike, not a misattribution — a water-table claim that did not carry limitation_structural_3. Cost: about 1,300–1,700 extra prompt tokens against per-run totals of 40–78k.

What binds a claim

What a caveat is, and where the surviving ones come from

A caveat is a record, not a sentence — five fields, so it can be checked. An unrespected caveat written as prose looks exactly like a respected one.

{"id": "limitation_structural_2",
 "severity": "blocking",
 "statement": "Local runoff generation on a 1 m² column, not routed discharge…",
 "applies_to": "any comparison against a stream gauge",
 "source": "experiment.json:limitations"}

Severity is what the caveat does to a claim, not how bad it sounds. blocking — the claim must not be made, or must carry the id, and this is the only one the audit enforces. qualify — may be made, stated with this attached. context — worth knowing, constrains nothing by itself.

applies_to is not decoration: step 3 matches a claim's own words against it. Scope wording that names the subject ("recharge, drainage and any water-table claim") works; wording that names the machinery ("the water_table comparison") does not.

One producer now, not three

As of 2026-08-13 caveats come from step 0 alone — read out of experiment.json, where the Experiment Manager put them. They say what the study's scope and the model choices allow, which is what a caveat was for. On both runs: 14, of which 5 blocking.

sourcenwhat it says
experiment.json:limitations8 Structural and configuration limits of the run design — a 1 m² unrouted column, a one-year record, a warm start whose inherited storage is not in equilibrium with this basin's forcing.
experiment.json:assumptions_ledger6 What the planner and the expander assumed to make the study runnable, each tagged with who assumed it — reception, the user, a default, or the sampler.
step2_investigate0–1 One kind only: a planned figure that failed to produce a usable result. context.

Step 1's eight are gone. Every one of them restated a number the summary already carried — and the interpreter reads that summary, which is 43% of its brief against the caveats' 24%. What was lost is enforcement, not information.

For review

Seven things I would question

The citation rule strikes true sentences

Resolved 2026-08-13. It was never the rule. The brief showed step 1's evidence in one shape and step 2's in another, and cut every result at 700 characters — so the model was quoting from evidence it could only partly see, under ids it had no uniform list of. Showing it exactly what the audit accepts took the strike rate from 9 of 14 to 1 of 21. The remaining strike is a caveat the claim genuinely owed.

The audit now has five generic caveats and no run-specific ones

Removing step 1's caveats was right — they restated measurements the interpreter could already see, and they were never shown to it as rules, only used to strike it afterwards. But it leaves limitations.py as the sole source of anything blocking, and its five entries are the same on every run. Nothing run-specific can bind any more.

Whether that matters is an empirical question, and the run to answer it is Naches: sixteen of sixteen columns sit below the active soil, and the interpreter is now trusted to notice that in below_active_soil and reason accordingly rather than being struck for missing it.

Two rounds is the whole budget

Brandywine spent both and still returned insufficient — correctly, and for a reason knowable at step 0: the field it needed was not in any frame. Four model calls to discover a packaging defect. The catalogue now names what is absent and why, which is the cheap half of the fix; the expensive half would be refusing a figure the frames cannot support before a model is asked to write it.

A refused pin looked exactly like a column that was never pinned

Three separate breaks had to be repaired before a designed pin survived to the comparison: a spelling gap between the sampler and the Spec, a join that dropped the three pin fields, and the fact that neither failure printed anything. Nothing in the record distinguished "no pin was designed" from "the pin was silently discarded" — worth a diagnostic of its own, since the same shape will recur.

The same shape recurred twice more the same day

A capability probe tested row["soil"]["clay_max_pct"], a field null on 100% of columns across every run ever packaged, while soil_profile beside it was complete. So the soil figures were never offered, on any run, and nothing said so. Separately, three standalone CLIs were still asking for four metric names that had been renamed hours earlier — their driver tables would have come back nearly empty and looked like a measured result.

Both are the failure this page keeps describing: a null that means "not computed" rendering identically to one that means "computed as nothing." The fix in both cases was to make the absent case say its own name — responses.unmeasured now carries a reason per response, the way the drivers already did.

Naches has never produced an interpretation

It does now — all five steps, 11 claims, verdict insufficient. What made the earlier attempt fail is still unknown; it did not recur on a clean replay, so it was most likely a transient rather than a defect, and I am recording that as a guess rather than a diagnosis.

The verification found the bug that verification exists to find

Re-running the extract stage surfaced a stale variable left by an earlier refactor: the honesty payload was assigned to a name that no longer existed, the NameError was swallowed by a bare except Exception, and it printed "limitations payload unavailable" — which reads as a run with no limitations rather than as code that did not run.

Since step 1 stopped deriving caveats that morning, that payload is the only source of anything blocking. Every future run would have had an interpreter with no constraints at all, announced as a warning. The handler now raises on a code fault and warns only on genuinely absent input — but the general shape, a bare except turning a bug into a data condition, is worth hunting elsewhere.
